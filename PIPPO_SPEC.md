# PIPPO — Build Prompt for OpenCode

Paste this entire document as your first prompt to OpenCode. It contains the full spec — architecture, data model, business logic, screens, and build order. Build it in the phases listed at the bottom rather than trying to do everything in one pass.

---

## 1. What we're building

Pippo is a **private, single-user Android study companion**, built as a personal gift for one specific person. It is NOT a general-purpose app, has NO multi-user support, NO login, NO server, NO cloud, NO analytics, and NO external API calls at runtime. Everything runs and persists entirely on-device.

The core loop: she imports study material (flashcards/MCQs) as JSON generated by NotebookLM. She studies 50 cards a day. A character named Pippo reflects her consistency — happy and thriving if she keeps her streak, increasingly sad if she's close to missing a day, dead if she breaks the streak with no freeze available.

## 2. Tech stack (use exactly this)

- **Framework**: React Native + Expo + TypeScript
- **Navigation**: Expo Router
- **Local database**: SQLite via `expo-sqlite` (not AsyncStorage — we have relational data: subjects → decks → cards, weak-card relationships, daily stats, study sessions)
- **Notifications**: `expo-notifications`, fully local/scheduled — no push server
- **Sharing/backup**: `expo-sharing` (Android share sheet — no Google auth, no API keys, ever)
- **Charts**: try a lightweight RN chart library first; if it's fights to configure, build simple bar charts with plain Views + flexbox — don't over-engineer this
- **Character assets**: compressed `.webp` static images, no animation library
- **Build target**: Expo/EAS → Android APK, keep total app size under 100MB (compress all image assets, avoid unnecessary dependencies)

No backend, no user accounts, no authentication anywhere in this app.

## 3. Database schema (SQLite)

```sql
subjects (
  id, name, created_at
)

decks (
  id, subject_id, name, created_at
)

cards (
  id, deck_id, question, answer, created_at
)

mcqs (
  id, deck_id, question, options_json, correct_answer_index, explanation, created_at
)

weak_cards (
  card_id, marked_at    -- presence in this table = weak; absence = strong
)

weak_mcqs (
  mcq_id, marked_at     -- presence in this table = weak; absence = strong
)

daily_stats (
  date, items_completed, flashcards_completed, mcqs_completed, study_seconds
)

study_sessions (
  id, start_time, end_time, source, subject_id, deck_id
)

streak (
  current_streak, longest_streak, last_completed_date, freeze_count
)

import_history (
  id, imported_at, subject, deck, card_count
)
```

Weak-item tracking uses two separate tables, not a strength score: a flashcard is weak if it is present in `weak_cards`, and an MCQ is weak if it is present in `weak_mcqs`. Removing the respective row means the item is no longer weak. Both weak-item tables have foreign keys to their respective item tables and cascade on delete.

`daily_stats.items_completed` is the authoritative count for the daily 50-item goal and must equal `flashcards_completed + mcqs_completed`. Dates in `daily_stats` and streak logic use the device's local calendar date in `YYYY-MM-DD` format; timestamps represent actual time intervals. `study_sessions.subject_id` and `study_sessions.deck_id` are nullable so manual timers can remain unassigned while item-based sessions can support future per-subject statistics.

## 4. Core business logic

### 4.1 Streak engine

- A day is "completed" when `daily_stats.items_completed >= 50` for that date.
- On completion: `current_streak += 1`; if `current_streak > longest_streak`, update `longest_streak`.
- Every 7 consecutive completed days: `freeze_count += 1`.
- If she misses a day (no completion recorded for a calendar date and the day has fully passed):
  - If `freeze_count > 0`: **ask her** whether to use a freeze (do not auto-consume it). If she confirms, decrement `freeze_count`, streak survives.
  - If she declines, or `freeze_count == 0`: streak resets to 0, Pippo enters the "dead" state.

### 4.2 Flashcard engine

Flow: show question → she taps "Show Answer" → answer reveals → she taps "Yes I knew it" or "No" → card counts toward the daily 50 regardless of which she picks.

- "No" → insert into `weak_cards`.
- "Yes" → remove from `weak_cards` if present.

### 4.3 MCQ engine

Show question + 4 options → she selects one → show correct/incorrect + explanation → counts toward daily 50.

- Wrong answer → insert into `weak_mcqs`.
- Correct answer → remove from `weak_mcqs` if present.

### 4.4 Weak card review mode

A dedicated study mode that only pulls flashcards present in `weak_cards` and MCQs present in `weak_mcqs`. When she gets one right, remove it from the appropriate table. This is the only "spaced repetition"-like behavior needed — keep it this simple, don't build a full SM-2 algorithm.

### 4.5 Random quiz / "Surprise Me"

- **Random quiz**: she picks a specific subject, a specific deck, or "All subjects" — pulls 50 random cards/MCQs from that scope.
- **Surprise Me**: an algorithm that fills 50 cards by: (1) preferring weak cards first, (2) including cards not recently seen, (3) mixing across subjects rather than pulling all 50 from one, (4) avoiding immediate repetition within the session. Keep the algorithm simple — weighted random selection is enough, no need for true ML-style recency scoring.

### 4.6 Emergency 5

A button on Home: "I don't want Pippo to die." Starts an immediate 5-card mini-session pulling from any due material. After 5 cards, show encouragement ("Good start. 45 more to go.") but do NOT mark the day as complete or affect the streak — its only purpose is lowering the activation energy to start studying, not a shortcut around the 50-card requirement.

### 4.7 Study timer (separate system from the 50-card streak)

- Manual timer: store `timer_started_at` as a timestamp, not a running JS interval — compute elapsed time as `current_time - timer_started_at` so it survives backgrounding, screen lock, and app switches.
- Automatic flashcard-time tracking: while she's actively answering cards, record that as study time too — but only when the manual timer is OFF. If the manual timer is ON, merge the two by computing the union of their time intervals (don't double-count overlapping time).
- Inactivity detection: if there's no interaction for 2-3 minutes on a flashcard/MCQ screen, pause automatic time tracking; resume on the next interaction.

### 4.8 Statistics, calendar, graphs

- `daily_stats` accumulates date, items_completed, flashcards_completed, mcqs_completed, and study_seconds — all computed locally, no external analytics.
- Calendar view: one cell per day showing study time and a streak indicator (🔥 for a day where the 50-card goal was hit, 💀 for a miss). Tapping a day shows a breakdown: total time, cards, MCQs, and a per-subject time split for that day.
- Weekly graph: simple bar chart of study time per day for the current week, plus a comparison line to last week (e.g. "+26% vs last week").
- Growth insights: derive simple sentences from the stored stats — longest study day, best week, % studied of last 30 days, this-week-vs-last-week comparison. If she's down vs last week, use a gentle, non-punishing tone (e.g. "You've studied less this week than last — that's okay, let's pick it back up").

### 4.9 Character states

Static image swap only, no animation framework:

```
neutral, slightly_sad, sad, disappointed_angry, happy, very_happy, celebration, dead
```

A single function `getCharacterState(streak, todayProgress, freezeAvailable)` returns which state to display, mapping to `assets/pippo/{state}.webp`. Milestone days (7/14/21/30/50/100) can trigger a special `celebration` state and unlock a personal message (see 4.12).

### 4.10 Notification engine

All messages are pre-written, never AI-generated at runtime. Write 5-8 variants per category so it doesn't feel repetitive; pick randomly each time. Categories:

| Category      | Timing                                                                                                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hydration     | ~every 2 hours during waking hours                                                                                                                                               |
| Study nudge   | ~3 hours after she last opened the app — **reschedule this one every time she opens the app** (cancel pending, schedule fresh 3h out); stop firing once she's hit 50 for the day |
| Talk-to-me    | ~every 6 hours                                                                                                                                                                   |
| Encouragement | Every 3-4 days (randomize the exact gap)                                                                                                                                         |
| Sleep         | After 10pm, 3-4 reminders that get slightly more direct as the night goes on                                                                                                     |
| Weak cards    | Occasional reminder to go review weak cards                                                                                                                                      |
| "I miss you"  | Very occasional (rarer than encouragement)                                                                                                                                       |

Respect a configurable quiet-hours window (default 10:30pm-7:00am) for all categories except the sleep-reminder category itself. Build a Settings screen with a per-category on/off toggle — this is required, not optional, given the notification volume.

### 4.11 NotebookLM import + validation

Two screens under Import: "Generate Flashcards" and "Generate MCQs," each showing a copyable prompt (exact text below in section 6). After she pastes the JSON NotebookLM returns:

1. Strip markdown code fences if present (`json ... `).
2. Locate the JSON object/array within the text.
3. Parse it; on failure, show a clear human-readable error (not a raw stack trace).
4. Validate required fields exist and are the right type.
5. Show a summary before committing: "✅ Valid JSON, 87 cards found."
6. Let her choose or create the subject, and choose or create the deck, before the final Import tap.

### 4.12 Personal content

Build a small `constants/personalMessages.ts` file she — or you — can hand-edit:

- One long-form "A Note From Pippo" (a letter from you, shown from a menu item).
- Milestone-specific messages for 7/14/21/30/50/100 days.
- A pool of everyday random Pippo messages shown on Home.

Keep this in a separate constants file so it's trivial to edit without touching logic code.

### 4.13 Backup / restore

- "Export Backup" bundles subjects, decks, cards, MCQs, weak cards, streak, freezes, daily stats, and settings into one JSON file named `pippo_backup_{date}.json`.
- Hand it to Android's native share sheet (`expo-sharing`) — she chooses where it goes (Gmail, Drive, Files, WhatsApp, whatever). The app never touches any account credentials.
- "Restore Backup" reads a previously exported file back in and repopulates the database, with a confirmation step before overwriting existing data.

## 6. NotebookLM prompts (build these into the Import screens as copyable text)

**Flashcard prompt:**

```
Based on all uploaded sources, generate 50 flashcards covering the key concepts.
Output ONLY valid JSON in this exact format, no markdown code fences, no explanation before or after:

{
  "subject": "short subject name",
  "flashcards": [
    {"question": "string", "answer": "string"}
  ]
}
```

**MCQ prompt:**

```
Based on all uploaded sources, generate 30 multiple-choice questions covering the key concepts.
Output ONLY valid JSON in this exact format, no markdown code fences, no explanation before or after:

{
  "subject": "short subject name",
  "questions": [
    {"question": "string", "options": ["string","string","string","string"], "correctIndex": 0, "explanation": "string"}
  ]
}
```

## 8. Build order (do NOT attempt everything in one pass)

1. **Phase 1 — Core loop**: SQLite schema + migrations, Subjects/Decks/Cards data layer, JSON import + validation, Flashcard and MCQ study screens, daily 50-card counter.
2. **Phase 2 — Streak + character**: streak engine, freeze logic, character state mapping, Home screen tying it together.
3. **Phase 3 — Weak cards + variety**: weak-card tracking, Weak Cards mode, Random Quiz, Surprise Me, Emergency 5.
4. **Phase 4 — Time + stats**: study timer with timestamp-based elapsed calc, timer/flashcard-time merging, inactivity detection, daily_stats writes, Calendar, Weekly Graph, growth insights.
5. **Phase 5 — Notifications**: all categories, message pools, rescheduling logic for the study nudge, quiet hours, per-category settings toggles.
6. **Phase 6 — Backup + polish**: export/restore via share sheet, personal content (letter + milestone messages), final asset compression pass, EAS build to APK, verify final size under 100MB.

Confirm each phase works before moving to the next — this keeps debugging manageable and avoids compounding errors across a large single-shot build.
